Code-First and Migrations

The schema comes from the classes. Every change is recorded,
ordered and replayable — on every machine.

Lecture 4 · Code-first, annotations, migrations, seeding~180 min · demo-heavy

Where we left off

Session 07 ended on a deliberate failure

We built everything the application needs to talk to a database — and then the application asked for a table that nobody had ever created.

What we already have

An Article class, a context, a connection string, and dependency injection wiring it all together.

What is missing

What we do about it

We create it from the classes we already wrote — without hand-writing SQL, and in a way our teammates get too.

Recap and the missing table

The application is ready. The database is not.

SqliteException: SQLite Error 1:
  'no such table: Articles'
   at Microsoft.Data.Sqlite.SqliteDataReader...
   at SimpleBlog.Controllers.ArticlesController.Index()
  • The class exists — we wrote it.
  • The context exists — it exposes DbSet<Article>.
  • The connection works — that is why we get a database error and not a connection error.
  • The table has never been created.
Two ways forward. We could open the database and write CREATE TABLE by hand — and repeat that on every machine, forever. Or we could make the classes produce the schema. That is the whole session.

The premise of this session

The classes we edit every day

Everything that follows is machinery for keeping a real database, with real rows in it, in step with those classes — as they keep changing.

Two directions, and the problem neither of them solves

Nothing in this block belongs to one language or one tool.

Microsoft Web Technologies

Two directions

Who writes the schema, and who generates it?

ApproachWe writeThe tool generatesSuits
Database-firstthe schemathe classesan existing database we inherited, or one a separate team owns
Code-firstthe classesthe schemanew applications, where the classes are what we touch every day

Neither is "correct"

They answer different situations. Plenty of serious systems use each one.

This course uses code-first

We are building something new, and it makes the classes the single source of truth — one place to look, one place to change.

Microsoft Web Technologies

The real problem

"Generate the database from the classes" works exactly once

Week 1

The article has a title and a body. We create the database.

Week 2

We add a summary.

Week 3

We rename the author field and make the title required.

  1. The database already holds 500 rows. Can we delete it and recreate it? No — that is people's data.
  2. A colleague pulled our code. How does their database learn about the summary?
  3. The live server still has the old schema. How does it get updated, at deploy time, safely?
  4. The change was wrong. How do we go back?
Microsoft Web Technologies

The answer, in the abstract

Record every schema change as an ordered,
versioned, repeatable script — stored next to
the code that needs it.

Each one knows how to move the schema forward, and how to move it back. One such recorded change is called a migration.

Microsoft Web Technologies

The migration timeline

One order for everyone; each machine applies what it is missing

Same track, same order, three different positions. Catching up is never a decision — it is replaying what is missing.

Microsoft Web Technologies

Why replaying is safe

The database keeps its own list of what it has applied

Alongside our tables, the tool keeps a small bookkeeping table: one row per migration that this particular database has already run.

Running it twice is safe

The second run compares the list with the files on disk, finds nothing missing, and does nothing at all.

Every environment is self-describing

We never have to remember which server is at which version. We ask it.

Not a new idea

The same mechanism, under the same name, exists in Rails, Django, Flyway, Liquibase and Alembic. The vocabulary transfers.

This is why "apply migrations" can be a step in an automated deployment. It is safe to run on a database that is already up to date.
Microsoft Web Technologies

Two rules

These two prevent nearly all migration pain

Rule 1

A migration that has been shared or deployed is history

Never edit it. Someone else's database has already applied that exact file; changing it now means two databases with the same version number and different shapes. Add a new migration instead.

Rule 2

Read the generated migration before applying it

The tool compares two states and guesses what happened between them. A rename is easily guessed as "drop one column, add another" — which silently destroys every value in it.

Describing the rules on the model

The schema needs answers the class does not give

Which columns may be empty? How long may a title be? Is that a date or a moment in time? Which column identifies a row?

Convention

The tool assumes sensible defaults. A property called Id is the identifier — nobody has to say so. Conventions keep the common case silent.

Explicit declaration

We annotate the exceptions: this one is required, that one is at most 200 characters, this one is a date. Every tool of this kind offers both.

These declarations pay twice. They shape the database, and — in Session 09 — they check what people type into forms. One statement, two jobs, which is exactly why the model is the right place to put it.
Microsoft Web Technologies

In practice · from here on, the names are concrete

The same four ideas, with their .NET names

The ideaWhat it is called in EF Core

The tooling is a separate program from the application. We install it once, globally: dotnet tool install --global dotnet-ef, then check it with dotnet ef --version.

Data annotations

We say the rules on the class itself

using System.ComponentModel.DataAnnotations;

public class Article
{
    public int Id { get; set; }   // key

    [Required]
    [MaxLength(200)]
    [Display(Name = "Article title")]
    public string Title { get; set; } = "";

    [Required]
    [MaxLength(100)]
    public string Author { get; set; } = "";
    [MaxLength(500)]
    public string? Summary { get; set; }

    [Required]
    [DataType(DataType.MultilineText)]
    public string Body { get; set; } = "";

    [DataType(DataType.Date)]
    [Display(Name = "Published on")]
    public DateTime PublishedOn { get; set; }
}
Microsoft Web Technologies

Data annotations

Some change the database. Some change nothing in it at all.

AnnotationEffect on the databaseEffect elsewhere
[Key]primary keyredundant when the property is already called Id
[Required]NOT NULLvalidation, and client-side rules — Session 09
[MaxLength(n)]a bounded text column instead of an unlimited onevalidation — Session 09
[DataType(…)]mostly nonewhich input control is rendered, and how values are formatted — Session 09
[Display(…)]nonethe label shown in views and forms — Session 09
Microsoft Web Technologies

Data annotations

Three things to be precise about

string? versus string

With nullable reference types on — the default in modern .NET — a plain string is already treated as required. [Required] makes the intent explicit and drives the message the user sees.

[MaxLength] is not decoration

Without it every text column is unbounded: slow to index, impossible to validate, and a free invitation to paste a novel into a title field.

The Fluent API exists

Anything annotations cannot express — composite keys, relationships, indexes — is configured in code in OnModelCreating. We name it so it is not a surprise; we do not use it here.

Migrations: create, inspect, apply, roll back

Four commands, and one habit that matters more than all of them.

Microsoft Web Technologies

Creating the first migration

One command — and then we stop and read

dotnet ef migrations add InitialCreate

Nothing has happened yet

No database was touched. The tool compared our classes to its record of the previous state and wrote a file describing the difference.

The name is documentation

InitialCreate, AddTagsToArticle, RequireArticleTitle. Someone will read this list in a year — probably us.

Reading it is the point

This is the most valuable five minutes of the session. We open the file and walk it line by line against the annotations we wrote.

Microsoft Web Technologies

The code-first round trip

The class is the source. The table is the output.

Microsoft Web Technologies

Reading the generated migration

Every annotation we wrote has a visible consequence

protected override void Up(MigrationBuilder b)
{
    b.CreateTable(
        name: "Articles",
        columns: table => new
        {
            Id      = table.Column<int>(nullable: false),
            Title   = table.Column<string>(maxLength: 200, nullable: false),
            Summary = table.Column<string>(maxLength: 500, nullable: true)
        },
        constraints: table => table.PrimaryKey("PK_Articles", x => x.Id));
}

[MaxLength(200)] → maxLength: 200 · [Required] → nullable: false · string? → nullable: true · Id → primary key, and an autoincrement annotation, by convention.

Microsoft Web Technologies

Reading the generated migration

Down goes back; three files make it possible

protected override void Down(MigrationBuilder b)
{
    b.DropTable(name: "Articles");
}

The migration

20260304…_InitialCreate.cs — the timestamped pair of Up and Down. The timestamp is what puts migrations in order.

The designer file

….Designer.cs — the model as it looked immediately after this migration.

The snapshot

ApplicationDbContextModelSnapshot.cs — the current state, which the next migrations add diffs against. Never edit it by hand.

Microsoft Web Technologies

Seeing the SQL without touching the database

The ORM was never hiding anything from us

dotnet ef migrations script
CREATE TABLE "Articles" (
    "Id"          INTEGER NOT NULL
                  CONSTRAINT "PK_Articles" PRIMARY KEY AUTOINCREMENT,
    "Title"       TEXT NOT NULL,
    "Summary"     TEXT NULL,
    "Body"        TEXT NOT NULL,
    "PublishedOn" TEXT NOT NULL
);

This closes the loop with Session 07's SQL primer. We can always ask to see the statement — and on a production database, this script is what a database administrator reviews before anything runs.

Applying it

Now the database exists

dotnet ef database update
Done.

Articles

The columns, types and nullability we predicted from the annotations. We open the file in a SQLite viewer and check every one.

__EFMigrationsHistory

One row: InitialCreate. This is the whole trick — the database's own record of what it has run.

Run it again

Nothing happens. The list already contains everything on disk. Safe, and boring, exactly as designed.

We run the application. The Session 07 error is gone and the page loads with an empty list. An empty list is a success.

Changing the schema

A second migration adds a column — it does not rebuild the table

[MaxLength(50)]
public string? Tags { get; set; }
dotnet ef migrations add AddTagsToArticle
dotnet ef database update
b.AddColumn<string>(
    name: "Tags",
    table: "Articles",
    maxLength: 50,
    nullable: true);
AddColumn, not CreateTable. Existing rows survive untouched, with NULL in the new column. That is the point of migrations.
Microsoft Web Technologies

Going back

Three levers, in increasing order of damage

dotnet ef database update InitialCreate
// move the database to that migration — Down() runs

dotnet ef migrations remove
// delete the last migration file, if never applied

dotnet ef database drop
// deletes the whole database. Development only.
database drop on anything with real rows in it is not a rollback. It is data loss with a friendly command name.
CLIPackage Manager Console
migrations addAdd-Migration
database updateUpdate-Database
migrations removeRemove-Migration
migrations scriptScript-Migration
Microsoft Web Technologies

The cycle

Five steps, in this order, every time

  1. Change the model class.
  2. dotnet ef migrations add <DescriptiveName>
  3. Read the generated migration.
  4. dotnet ef database update
  5. Run the application.

Step 3 is the one people skip

Steps 1, 2, 4 and 5 fail loudly when they go wrong. Step 3 is the only one that catches a mistake before it reaches data — which is the only moment at which it is still cheap.

Seeding initial data

An empty database makes for a poor demo and slower development.

Microsoft Web Technologies

Seeding

Known starting data, recorded in the schema history

protected override void OnModelCreating(ModelBuilder b)
{
    b.Entity<Article>().HasData(
        new Article { Id = 1, Title = "How the web works",
              Author = "Ada", Body = "...",
              PublishedOn = new DateTime(2026, 1, 10) },
        new Article { Id = 2, Title = "Getting started",
              Author = "Grace", Body = "...",
              PublishedOn = new DateTime(2026, 2, 2) }
    );
}
dotnet ef migrations add SeedArticles
dotnet ef database update
The one surprise: with HasData we must set Id ourselves, even though the database normally generates it. EF Core needs stable identities to tell an insert from an update across migrations.
The alternative — a seeding method called at application start — suits data that should not live in migration history at all. We name it; we use HasData.

The payoff from Session 02 — with the generated SQL on screen the whole time.

Microsoft Web Technologies

Querying

Four shapes cover almost everything we need

// all, newest first
var all = await _context.Articles
    .OrderByDescending(a => a.PublishedOn)
    .ToListAsync();

// one, or null
var article = await _context.Articles
    .FirstOrDefaultAsync(a => a.Id == id);
// filtered and projected
var titles = await _context.Articles
    .Where(a => a.Author == author)
    .OrderBy(a => a.Title)
    .Select(a => a.Title)
    .ToListAsync();

// read-only listing, measurably faster
var list = await _context.Articles
    .AsNoTracking().ToListAsync();
AsNoTracking tells EF Core we are not going to change these objects, so it need not keep a copy to compare against later. For a page that only displays rows, that is free speed.
Microsoft Web Technologies

Querying

Why every one of those had await in front of it

A database call waits

The query leaves the machine and the answer takes milliseconds to come back. Without await, a thread sits and stares at the network for all of them.

await frees the thread

It goes and serves somebody else's request in the meantime, and picks ours back up when the answer arrives.

The rule for this course

Use the …Async methods, and make the action public async Task<IActionResult>. The theory can wait; the pattern cannot.

async does not make one request faster. It makes the server able to handle more of them at once.
Microsoft Web Technologies

Querying

Deferred execution — and the trap it sets

.Where(…) builds a query. .ToListAsync() runs it. One round trip happens, at the end, with everything combined.

.Where(…).ToList() 
SELECT "a"."Id", "a"."Title", "a"."Author"
FROM "Articles" AS "a"
WHERE "a"."Author" = @__author_0
ORDER BY "a"."Title"
.ToList().Where(…) 
SELECT "a"."Id", "a"."Title", "a"."Author",
       "a"."Body", "a"."Summary", ...
FROM "Articles" AS "a"

-- 500 000 rows, then filtered in memory
EF Core logs its generated SQL to the console in Development. We keep that terminal window visible for the rest of the session — reading it is how the trap becomes obvious rather than theoretical.
Microsoft Web Technologies

Closing the loop

The controller changed. The view did not.

public async Task<IActionResult> Index(string? author)
{
    var q = _context.Articles.AsNoTracking();
    if (!string.IsNullOrWhiteSpace(author))
        q = q.Where(a => a.Author == author);

    var articles = await q
        .OrderByDescending(a => a.PublishedOn)
        .ToListAsync();

    return View(new ArticleListViewModel
        { Articles = articles });
}

Separation of concerns, paying a dividend

Session 06's view model insulated the page from where its data came from. The rows now arrive from a real database instead of a hard-coded list, and the Bootstrap card grid and table render them without a single edit.

Optional · if time allows

Related rows do not load by themselves

var articles = await _context.Articles
    .Include(a => a.Category)
    .OrderByDescending(a => a.PublishedOn)
    .ToListAsync();
Forget it and…

a.Category is null

Not an error, not an empty object — null, and the page falls over on the first attempt to read a name from it. EF Core does not fetch what we did not ask for.

We watch the generated SQL with and without Include: one is a JOIN, the other is not. That is the entire mechanism.

Common misconceptions

Ten things that are almost right

MisconceptionCorrection
"A migration is the database."It is one recorded change to it.
"Migrations run automatically."We run them. Production is Session 10.
"Edit the migration if it's wrong."Only if it was never shared or applied.
"Delete the database and start over."Fine on day one, catastrophic with real data.
"[MaxLength] is just validation."It changes the column too.
MisconceptionCorrection
"Annotations only matter to the database."They drive forms and validation — Session 09.
".Where() runs immediately."Nothing runs until ToList, First, Count.
".ToList().Where() is the same."The first loads the whole table into memory.
"async makes it faster."It lets the server serve more requests.
"Related data loads by itself."Not without Include. It will be null.

Walkthrough · 30 min · from the front

Our database, our article list

  1. We annotate Article: title required and at most 200, author required and at most 100, summary optional and at most 500, body multiline, PublishedOn a date labelled "Published on".
