What routing is

A method, a path, and a decision to make.

Microsoft Web Technologies

What routing is

The request tells us almost nothing

GET /articles/42 HTTP/1.1
Host: simpleblog.example.com

A request arrives carrying a method and a path. Somewhere, something has to decide which piece of our code answers it.

Routing

That decision — matching an incoming method and path to the code that handles it.

A route

One piece of configuration describing part of that decision. An application has several; together they are the routing table.

Microsoft Web Technologies

What routing is

Analogy: the switchboard

  • A call comes in asking for extension 42.
  • The operator does not know what happens on extension 42, does not do the work, and does not care what it is about.
  • The operator knows exactly one thing: how to connect a number to a desk.
  • Routing is the switchboard between URLs and code.

Two separate jobs

Deciding who answers is one job. Answering is a different one — that was Session 03, and it stays untouched here.

Microsoft Web Technologies

What routing is

Why this is a topic at all

1995

A URL was a file path

/products/shoes.html meant a file named shoes.html inside a folder named products, on a disk.

Adding a page meant adding a file. Renaming a page meant renaming a file. Nobody designed URLs, because the folder layout designed them.

Now

A URL is a name we choose

The path is interpreted by our program. Nothing on disk has to match it. /articles/42 is not a folder, and 42 is not a file.

That freedom is exactly why routing exists — and why URL design became a job someone has to do.

Microsoft Web Technologies

URLs as a public interface

Why URLs deserve design effort

They are the most public part of the app

People read them, type them, paste them into chats, print them on posters and read them aloud over the phone.

They are permanent

The moment someone bookmarks or links to a URL, changing it breaks their link — and we never find out.

They are the table of contents

A good URL tells a stranger what the page is before it loads.

Search engines read them

The path is one of the few pieces of text a search engine sees for every single page.

Microsoft Web Technologies

URLs as a public interface

"Cool URIs don't change."

Tim Berners-Lee, 1998. The person who invented the URL spent an essay on the argument that the hardest part is choosing one you will not want to change.

Block 3 · 20 min

URL design principles

Six rules that survive any language, any framework, any decade.

Microsoft Web Technologies

URL design principles · 1 of 2

Nouns, hierarchy, lowercase

  1. Nouns for things, not verbs. /articles/42, not /getArticle?id=42. The verb is already in the method — Session 01.
  2. Hierarchy with /, filters with ?. The path says which resource; the query string says how we want it. /articles/42/comments is a thing; /articles?author=ada&sort=new is a filtered view.
  3. Lowercase, hyphen-separated. /article-archive, not /ArticleArchive and not /article_archive. Paths are case-sensitive on many servers; nobody should have to guess.
Microsoft Web Technologies

URL design principles · 2 of 2

Guessable, honest, consistent

  1. Stable and guessable. If /articles/42 exists, then /articles/43 should mean the analogous thing. Predictability is a feature, not a coincidence.
  2. No implementation leakage. .php, .aspx, /api/v2/internal/ — nobody outside the team should be able to tell what we built it in, or which of our layers they have landed on.
  3. Plural collections. /articles is the many; /articles/42 is one of them. Pick one style across the whole site and never mix.
All six are conventions, not laws. Their value is that thousands of sites already follow them, so a visitor arrives already knowing how to read our URLs.

The last three rows are the interesting ones

the form

Showing vs. saving

The form that shows the fields and the request that saves them can share one URL and differ only in method — GET then POST. That pairing is every form we write in Session 09.

delete

DELETE or POST?

DELETE is the honest method, but browser forms only ever send GET and POST — Session 01. In a browser app we send a POST. Never a GET.

/about

The odd one out

"About us" is not one of a collection of things. It is a single page with a single name, and it should sit at the root — not underneath the articles.

Notice what we have just done: designed a public interface for the whole application, on paper, before writing a line of code. That order is deliberate.

Conventional routing in ASP.NET Core

One template, described centrally, that covers the whole application.

Microsoft Web Technologies

Conventional routing

The line that has been there since Session 02

// Program.cs
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

Every URL our project has answered so far was matched by that one string. It is not generated, not hidden, and not special — it is a string in a file we can edit.

Route template

A pattern describing a shape of path, written in segments separated by /, with the variable parts in braces.

Microsoft Web Technologies

Conventional routing

The template, piece by piece

PieceMeaning
{controller}A route parameter — whatever is in this segment names the controller.
=HomeIts default, used when the segment is absent from the URL.
{action}Whatever is in this segment names the action method.
=IndexIts default, on the same terms.
{id?}The ? makes this segment optional — the URL may simply stop before it.
Two of the three segments are not names of anything real. They are placeholders filled in from the URL at the moment the request arrives.

Conventional routing

Two halves of one contract

pattern: "{controller}/{action}/{id?}"

public IActionResult Details(int id)
{
    // id == 42
}

Routing extracts the value. Model binding — Session 03 — hands it to the parameter by name.

Rename one, rename both

Change the template to {articleId?} and leave Details(int id) alone, and nothing crashes — id quietly becomes 0.

We break it on screen, watch article 0 come back, then put it right. Silent zeros are far more expensive to find than errors.
Microsoft Web Technologies

Conventional routing · demo

These are just strings we control

// Make Articles the home page of the site
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Articles}/{action=Index}/{id?}");

One word changed. We save with dotnet watch running, reload /, and the blog is the front page of the site.

Nothing else moved

No controller, no action and no file was renamed. The URL changed because the route changed. That is the whole idea of routing, demonstrated in one edit.

Microsoft Web Technologies

Conventional routing · demo

Adding a route of our own

app.MapControllerRoute(
    name: "archive",
    pattern: "archive/{year:int}/{month:int}",
    defaults: new { controller = "Articles", action = "Archive" });

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

What it buys us

/archive/2026/3 now reaches Articles.Archive(int year, int month) — a URL with no controller or action name in it at all.

Note the order

The specific route is registered above the general one. The next slide explains why that is not a matter of taste.

Microsoft Web Technologies

Conventional routing

Routes are tried in order, and the first match wins

The rule

Routes are tried in the order they are registered. The first one that matches answers the request; the rest are never consulted.

The consequence

Specific routes go above general ones. A general route placed first will swallow every path that a later, better route was written for.

Microsoft Web Technologies

Conventional routing · demo

The bug we cause on purpose

We register default first and archive second, then request /archive/2026/3.

// what the default route makes of it
controller = archive
action     = 2026
id         = 3

→ no ArchiveController exists → 404

Why this is worth ten minutes

The error message says not found. The template that caused it is thirty lines away and looks entirely innocent.

Nothing in the failure points at ordering — which is exactly why the rule has to be memorised rather than debugged.

Then we move the two lines back and watch the same URL start working, with no other change.

Block 6 · 25 min

Attribute routing and constraints

Describing a URL next to the code that answers it.

Microsoft Web Technologies

Attribute routing

Two places to put the same decision

Conventional

Described centrally

One list of templates in Program.cs describes the shape of every URL in the application.

Open one file and see the whole URL space. Change one line and a hundred URLs move.

Attribute

Described locally

Each action carries its own URL, written directly above it as an attribute — a labelled note attached to a class or a method that the framework reads.

The URL and the code that answers it are never out of sight of each other.

Both are valid, and most real projects mix them: conventional for the broad shape, attributes wherever a specific URL is wanted.
Microsoft Web Technologies

Attribute routing · demo

The blog's URLs, written where the code is

[Route("articles")]              // prefix for every action here
public class ArticlesController : Controller
{
    [HttpGet("")]                // GET /articles
    public IActionResult Index() { ... }

    [HttpGet("{id:int}")]        // GET /articles/42
    public IActionResult Details(int id) { ... }

    [HttpGet("by/{author}")]     // GET /articles/by/ada
    public IActionResult ByAuthor(string author) { ... }

    [HttpGet("/about")]          // leading / = absolute: /about
    public IActionResult About() { ... }
}
Microsoft Web Technologies

Attribute routing

Four things to take from that file

  1. [Route] on the class is a prefix; [HttpGet("…")] on the action completes it. The two are concatenated with a /.
  2. A leading / escapes the prefix entirely and gives an absolute path — that is how /about avoids becoming /articles/about.
  3. [HttpGet], [HttpPost], [HttpPut] and [HttpDelete] bind the method as well as the path. The same URL can have one action for GET and another for POST — the shape of every form in Session 09.
  4. Once a controller has attribute routes, conventional routes no longer reach it. /Articles/Details/42 stops working the moment we do this. That is intended, and it surprises everyone once.
Microsoft Web Technologies

Attribute routing

Which one do we reach for?

SituationReach forWhy
Dozens of controllers, all with ordinary list / detail / edit pagesConventionalOne template covers all of them. Adding a controller costs no routing work at all.
A URL that must read a particular way — /articles/by/adaAttributeThe shape is unique to that action, and belongs next to it.
Several actions sharing one path, split by methodAttributeMethod and path are declared together, in one place.
Segments that must be numbers, ranges, or a fixed lengthAttributeConstraints sit inline, right where the parameter is named.
A whole site whose URL shape may change laterConventionalOne central edit moves everything, as we saw two slides ago.
Microsoft Web Technologies

Route constraints

Saying what kind of value a segment may hold

[HttpGet("{id:int}")]              // only digits
[HttpGet("{slug:alpha}")]          // only letters
[HttpGet("{year:int:min(2000)}")]  // a minimum
[HttpGet("{month:int:range(1,12)}")]
[HttpGet("{code:length(3)}")]      // exact length
[HttpGet("{id:guid}")]

A filter, not validation

A constraint decides whether this route matches at all. It is not a check on user input — that is Session 09, and it is a different job with different error messages.

Constraints can be stacked: int and then range(1,12), separated by colons.
Microsoft Web Technologies

Route constraints · demo

Why they earn their keep

Without

/articles/banana

Matches Details(int id), binding fails, id silently becomes 0, and the visitor gets a confusing 404 for "article 0".

With

{id:int}

The same URL does not match this route at all, so it can fall through to a different one.

[HttpGet("{id:int}")]
public IActionResult Details(int id) { ... }

[HttpGet("{slug}")]
public IActionResult BySlug(string slug) { ... }
/articles/42 reaches Details. /articles/routing-basics reaches BySlug. One path shape, two meanings, separated only by a constraint.

Generating URLs

Ask the framework for the address. Never type it twice.

Microsoft Web Technologies

Generating URLs

Never hard-code a URL

If URLs are typed as literal strings across views and controllers, changing a route means hunting through the whole project — and missing some.

// in a controller
return RedirectToAction("Details", "Articles",
                        new { id = 42 });

// "/articles/42"
var url = Url.Action("Details", "Articles",
                     new { id = 42 });
@* in a view — the tag helper form, Session 05 *@
<a asp-controller="Articles"
   asp-action="Details"
   asp-route-id="42">Read</a>
We name the action and let routing produce the address. The route template stays the single place a URL is decided.
Microsoft Web Technologies

Generating URLs · demo

The most convincing sixty seconds of the session

articles → posts

We change one word

The [Route("articles")] prefix becomes [Route("posts")]. We save; dotnet watch rebuilds.

Every generated link survives

Each one asks routing for the address at the moment the page is rendered, and routing now answers /posts/42.

Every hard-coded link breaks

href="/articles/42" was a guess frozen into a file. It is now a 404, and nothing warned us.

Then we change it back. The lesson is not that posts is better — it is that a URL should be decided in exactly one place.

Wrap-up

Common misconceptions

MisconceptionCorrection
"The URL maps to a file on the server."It maps to whatever the routes say. Nothing on disk needs to match.
"Routes are matched by best fit."They are matched in registration order; the first match wins.
"A constraint validates user input."It decides whether the route matches. Input validation is Session 09.
"{id?} makes the parameter optional."The segment is optional. A missing int id becomes 0; use int? for real optionality.
"You must choose conventional or attribute routing."Projects routinely use both — but once a controller has attributes, conventional routes skip it.
"Query-string values need a route."No. Anything after ? is bound by name without appearing in any template.
"Changing a URL is harmless."Every existing link and bookmark breaks. Use a 301 — Session 01 — when something must move.

Check for understanding

Six questions

  1. With the default template, which controller and action does / reach? And is /Articles/42 the same as /Articles/Details/42?
  2. We register default first and archive/{year}/{month} second. What happens to /archive/2026/3, and why?
  3. What is the difference in behaviour between {id} and {id:int} when the request is /articles/banana?
  1. Write the attribute routing needed for GET /authors/ada/articles.
  2. A team renames /articles to /posts. Which links break, which fix themselves, and why?
  3. /articles?sort=new&page=2 — how many of those values appear in the route template? How do they reach the action?

Walkthrough · 30 min · on screen

We design and implement the blog's URLs

  1. We design on paper first: URL and method for all articles, one article, articles by an author, the archive for a year and month, about, contact — against the six principles.
  2. We implement that design with attribute routing on ArticlesController.
  3. We constrain id to an integer and month to range(1,12).
  1. We add /articles/{slug} returning Content($"slug: {slug}"), and confirm /articles/42 still reaches Details.
  2. We make /about absolute, not /articles/about.
  3. We replace every hard-coded URL with Url.Action or RedirectToAction, then rename the prefix to posts and back.
By the end we will have a SimpleBlog whose every URL was designed on purpose: /articles/banana reaches the slug action instead of failing, /articles/archive/2026/13 returns 404 on the range constraint, and renaming the prefix breaks nothing.
