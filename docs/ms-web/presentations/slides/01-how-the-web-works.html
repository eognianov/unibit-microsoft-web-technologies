The client–server model

Who asks, who answers, and in what order.

Microsoft Web Technologies

The client–server model

Analogy: the restaurant

  • You — the client — sit at a table and read a menu.
  • You give the waiter an order. That is a request.
  • The kitchen — the server — prepares it.
  • The waiter brings back your dish, or a message: "sorry, we're out of that." Either way, that is a response.

You never enter the kitchen

You never see how the dish is made. You only send requests and receive responses. The same is true of every website you have ever used.

Microsoft Web Technologies

The client–server model

Request, then response — always in that order

Two roles, not two machines

Client = the one who asks. Server = the one who answers. Your laptop can be both at once.

Many kinds of client

A browser is a client. So is a mobile app, a smart TV, or another program.

The server never speaks first

It is a program that is always listening on a machine that is always on. It only ever replies.

Microsoft Web Technologies

The client–server model

Every request is independent.
The server does not remember the previous one.

This is called statelessness. How sites nevertheless "remember" you — logins, shopping baskets — is a later topic.

Microsoft Web Technologies

The client–server model

What happens between clicking a link and seeing the page?

  1. You type or click a URL.
  2. The browser resolves the domain name to an address — DNS, like a phone book.
  3. The browser opens a connection to that address.
  4. The browser sends a request.
  1. The server does some work and sends a response — usually an HTML document.
  2. The browser reads the HTML, discovers it needs more files — CSS, images, scripts — and sends more requests, one for each.
  3. The browser draws the page.
Step 6 is the one to hold on to. We will watch it happen in the demo.
Microsoft Web Technologies

The number to remember

One page is not one request.

The browser reads that one document, finds everything it refers to, and asks for each of them separately. Exactly one of the 87 rows is the page.

Microsoft Web Technologies

The client–server model

What is HTTP?

Both sides must agree on the format of the messages. That agreement is a protocol.

HTTP

HyperText Transfer Protocol — the rules for how a web request and a web response are written down.

It is text

A request is human-readable. That is precisely why we can learn it by reading it — which is what we do next.

HTTPS

The same protocol, inside an encrypted tunnel. Same rules, private channel. Everything in this course applies identically.

Block 3 · 15 min

Anatomy of a URL

Six parts, each with one job.

Microsoft Web Technologies

Anatomy of a URL

Read it piece by piece

https://news.example.com:443/articles/42?lang=en&sort=new#comments
└─┬─┘   └───────┬───────┘└┬┘└────┬─────┘└───────┬────────┘└───┬───┘
scheme       host        port   path        query string   fragment

scheme

Which protocol — http or https.

host

Which server. Resolved to an address via DNS.

port

Which door on that server. Usually implied: 80 for http, 443 for https.

path

Which resource on that server. This is what we will design — Session 04.

query string

Extra named parameters, key=value, joined by &.

fragment

A position within the page. Never sent to the server.

Microsoft Web Technologies

Anatomy of a URL

Two facts worth stressing

/articles/42

The path is ours to interpret

The path is the part our application is responsible for reading and acting on. It is not a file path on a disk — not since about 1995.

#comments

The fragment never leaves the browser

It is stripped before the request is sent. The server has no idea it existed. This surprises people later — remember it now.

Block 5 · 25 min

The HTTP request

What the client actually sends.

Microsoft Web Technologies

The HTTP request

A real request, line by line

GET /articles/42?lang=en HTTP/1.1
Host: news.example.com
User-Agent: Mozilla/5.0 ...
Accept: text/html
Cookie: session=abc123
(blank line — then the body, if any)
  1. Method — what do you want done?
  2. Path and query — to which resource?
  3. Headers — metadata: who is asking, what formats they accept, what language they prefer, what cookies they carry. Name–value pairs, one per line.
  4. Body — the data being sent, if any. A GET has none. A form submission does.
This is plain text. Nothing here is hidden or magical — a request is something you could type by hand.
Microsoft Web Technologies

The HTTP request

Methods are verbs of intent

MethodIntentHas body?Safe?Idempotent?
GETGive me this resource.noyes — changes nothingyes
POSTHere is data — create or process it.yesnono
PUTReplace this resource with what I send.yesnoyes
DELETERemove this resource.usually nonoyes
Safe = does not change anything on the server.
Idempotent = doing it twice has the same effect as doing it once.
Microsoft Web Technologies

The HTTP request

Why "safe" is not a technicality

A browser will happily re-issue a GET — on the back button, on refresh, on prefetch. Search engines follow every link they find, without being asked.

If your "delete" is a GET, a crawler can wipe your database just by following links. This has happened to real sites, more than once.

In the browser

HTML forms only ever send GET and POST. That is a limitation of forms, not of HTTP.

In APIs

PUT and DELETE matter there. We name them now and use them later.

Block 6 · 25 min

The HTTP response

What comes back, and what the number at the top means.

Microsoft Web Technologies

The HTTP response

Status line, headers, body

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1543

<!DOCTYPE html>
<html>...</html>
  1. Status line — the protocol version and the outcome.
  2. Headers — metadata about the answer.
  3. Body — whatever was asked for: an HTML page, an image, a stylesheet, JSON data.
Content-Type is how the browser knows what those bytes are. The same bytes could be a page, a picture, or a font — the header decides.

Microsoft Web Technologies

Status codes

Two distinctions worth the minute

401 versus 403

401 — "Who are you?"

403 — "I know who you are, and no."

One is about identity, the other about permission.

4xx versus 5xx

This one tells you whose bug it is.

When your app returns a 500 in Session 10, that is your own code throwing an exception. A 404 is the server answering correctly.

No .NET yet — nothing to run. The tool every one of you already has: DevTools.

Microsoft Web Technologies

Demo

The DevTools Network tab

  1. Press F12 (or Cmd+Option+I) and select Network.
  2. Tick Preserve log and Disable cache.
  3. Load a content-heavy site and let the list fill up. One page — how many rows?
  4. Click the first row, the HTML document: request method, URL and status code; request headers Host, User-Agent, Accept, Cookie; response headers Content-Type, Content-Length; and the raw HTML in Response.
  1. Filter by type: Doc, CSS, JS, Img. One page, many kinds of resource.
  2. Type a deliberately wrong URL → a 404 row, in red.
  3. Visit an http:// URL that redirects → a 301/302 row with its Location header, then the follow-up request.
  4. Open a members-only page in a private window → a 401 or 403.
That raw HTML in the Response panel is what our app will spend the rest of this course producing.

Wrap-up

Common misconceptions

MisconceptionCorrection
"One page = one request."One page is dozens of requests: HTML, then CSS, JS, images, fonts.
"The server sends the whole website."The server answers one request at a time, with one resource each.
"The URL is the file path on the server."It used to be, in 1995. Today the path is interpreted by the app — Session 04.
"HTTPS is a different protocol."Same HTTP, wrapped in encryption.
"404 means the site is broken."404 means that resource does not exist. The server answered correctly.
"The server remembers me between requests."It does not, by default. Every request is independent.
"GET and POST are interchangeable."GET must never change data. Refresh, back button and crawlers repeat GETs freely.
"The #fragment is sent to the server."It never leaves the browser.
Microsoft Web Technologies

Check for understanding

Five questions

  1. In https://shop.example.com/products/17?color=red#reviews — which part does the server never see? Which part identifies the resource?
  2. A page says "You must be logged in to view this." Which status code — 401 or 403? What if it says "Admins only" and you are logged in?
  3. You click a link and the page appears; you click again and it appears again, unchanged. Which method was almost certainly used, and why does that matter?
  1. Your browser shows an error page. The status code is 500. Whose bug is it?
  2. Loading one news article produced 87 rows in the Network tab. Explain that number to someone who has never opened DevTools.

Walkthrough · 30 min · together

Let's investigate a website

We pick a public website and work through it on screen. Nothing to hand in — follow along on your own machine if you like, and stop me whenever a row does not make sense.

  1. We count the requests the home page makes, and find the largest single resource.
  2. We find one request of each type: a document, a stylesheet, an image.
  3. We read the full request line and three request headers of the main document.
  1. We read the status line and the Content-Type header of the response.
  2. We trigger a 404 and watch what the site does with it.
  3. We find a request whose status is not 200 and work out what happened.
By the end we will have named the method, path, status code and content type for at least three distinct requests, and explained one non-200 response.
