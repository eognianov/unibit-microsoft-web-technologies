Separation of concerns; the MVC pattern

Ideas only. No vendor, no language — these transfer to any stack.

Microsoft Web Technologies

Separation of concerns

One piece of code that does everything

when a request arrives for /articles/42:
    open the database connection
    run "SELECT * FROM articles WHERE id = 42"
    write "<html><body><h1>" + row.title + "</h1>"
    if user is admin: write "<a href=...>Edit</a>"
    write "</body></html>"
    close the connection

It works. It answers the request correctly.
What is wrong with it?

Microsoft Web Technologies

Separation of concerns

Four things go wrong, and they all go wrong slowly

Nobody can work alone

The designer who wants to move a heading has to edit the code that talks to the database.

Rules get copied

"Is this user an administrator?" is pasted into forty pieces of code. Changing the rule means finding all forty.

Nothing can be tested

To check one decision you need a database and a browser. So the decision is never checked.

Nothing can be reused

The data fetching is welded to the page text. Another page that needs the same data starts from scratch.

Microsoft Web Technologies

The principle

Separation of concerns:
each part of a program should have one reason to change.

A change of layout should touch layout code only. A change of rules should touch rules code only. Everything else stays where it is.

Microsoft Web Technologies

The MVC pattern

MVC is one very common way to apply that principle

ComponentResponsibilityIt must not
ModelThe data, and the rules about that data. "An article has a title; a title is required."Know that HTML or the web exist.
ViewPresentation. Turns data into what the user sees.Fetch data, or make decisions.
ControllerReceives the request, decides what to do, gathers the data, picks the view.Contain layout, or the deep business rules.
The pattern is older than the web by a decade. You will meet it again under other names in every large ecosystem — it is not the property of any one vendor.
Microsoft Web Technologies

The MVC pattern

Analogy: the restaurant, continued

Controller

The waiter

Takes your order, checks it makes sense, passes it to the kitchen, and brings back what comes out.

Model

The kitchen

Where the food is actually made, by rules that have nothing to do with your table.

View

The plating

Arrangement, garnish, the plate it is served on. How the result is presented to you.

The waiter does not cook. The chef does not choose the napkin colour.
Neither of them talks to your table without the other.

The MVC pattern

The traffic rule: who is allowed to talk to whom

Microsoft Web Technologies

The one rule to remember

Everything passes through the controller.

request → controller → asks model → data back to controller
        → controller hands data to view → response

Views never talk to the database. Models never write HTML. If you can state this rule at the end of the course, the course worked. We will point back at this slide in every session that follows.

Microsoft Web Technologies

The MVC pattern

What it buys, and what it costs

  • Change the design without touching the logic — and the logic without touching the design.
  • Two people can work on the same feature at the same time.
  • Logic can be checked without a browser in the way.
  • Somebody new to the project knows where to look. The structure tells them.
The honest cost

More files

A "hello world" becomes three files instead of one. The pattern looks like pure overhead at file 3.

The payoff arrives at about file 20 — and our app passes file 20.

The lifecycle of a request

Two things worth stressing before we write any code

Step 6 is yours

The framework calls you

This is the inversion from Session 02. You do not write the program that runs the web server; you fill in the interesting part, and something else calls it at the right moment.

Fresh every time

A new handler per request

One is created for each request and thrown away when the response is written. Never store something in it and expect it to survive — the web is stateless, exactly as in Session 01.

ASP.NET Core MVC

The same six stages, with their real names

Microsoft Web Technologies

Controllers

What a controller looks like

// Controllers/ArticlesController.cs
using Microsoft.AspNetCore.Mvc;

namespace SimpleBlog.Controllers;

public class ArticlesController : Controller
{
    public IActionResult Index()
    {
        return View();
    }
}
  • One file. One class. One method so far.
  • Every line of it is a convention — a rule the framework relies on without ever being configured.
  • That is the trade: follow the naming and everything is wired up for free; break it and nothing is wired at all.
Microsoft Web Technologies

Controllers

Five conventions, and what breaks without them

ElementRuleConsequence if broken
Locationin the Controllers/ folderConvention only — it works elsewhere, but do not do it.
Class nameends with ControllerNot discovered as a controller at all.
Base classinherits ControllerLoses View(), RedirectToAction(), NotFound(), and the rest.
Accessthe class is publicNot reachable.
Actiona public methodNot reachable as an action.
This is convention over configuration: the framework reads your names instead of asking you to write a configuration file listing every page.
Microsoft Web Technologies

Controllers

The name-stripping rule

public class ArticlesController : Controller     →   /Articles
public class HomeController     : Controller     →   /Home
public class AuthorsController  : Controller     →   /Authors

The word Controller is removed from the class name to make the URL segment.
This trips everybody up exactly once, and then never again.

Block 6 · 25 min

Returning results; getting parameters in

What comes out of an action, and how anything gets into one.

Microsoft Web Technologies

Actions

An action is one thing the app can do

A public method

An action is simply a public method on a controller. Nothing more exotic than that.

One capability each

List the articles. Show one article. Filter by author. Each is one action, each is one URL.

It returns a result

IActionResult is a promise to produce a response — it lets one method return different kinds of outcome.

One controller is not one page. It is one area of responsibility, with as many actions as that area needs.

Microsoft Web Technologies

Actions

The results you will use most

public IActionResult Index()   => View();            // 200 + HTML
public IActionResult Missing() => NotFound();        // 404
public IActionResult Denied()  => Forbid();          // 403
public IActionResult Old()     => RedirectToAction("Index");
public IActionResult Raw()     => Content("plain text");
public IActionResult Data()    => Json(new { id = 1 });
RedirectToAction sends a 302 and the browser asks again at the new address. Json sends application/json instead of HTML.
These are the status codes from Session 01 — 200, 302, 403, 404. The difference is that we are now the ones choosing them.

Getting data in

Model binding: the framework fills your parameters

// GET /Articles/Details/42        (route value 'id')
public IActionResult Details(int id)
    => Content($"Article {id}");

// GET /Articles/Search?term=http&page=2   (query string)
public IActionResult Search(string term, int page = 1)
    => Content($"Searching '{term}', page {page}");

We never open the request ourselves and pull values out of it. We declare the parameters we want, and they are there when the method starts.

Microsoft Web Technologies

Getting data in

Five rules of binding

  • The name is the contract. ?term=http fills string term, and nothing else. Rename the parameter and the link stops working.
  • Types are converted for you. ?page=2 arrives as the number 2, not the text "2".
  • A value that cannot be converted — ?page=abc — gives you 0 and a recorded error. Acting on that error is validation, in Session 09.
  • A default value makes a parameter optional: int page = 1.
  • string? marks a value that may legitimately be absent.

Where values come from

· the route path — /Articles/Details/42

· the query string — ?author=Ada

· the body of a submitted form — Session 09

Same mechanism, three sources.

Microsoft Web Technologies

Getting data in

A parameter that may not be there at all

// GET /Articles/Filter?author=Ada    → "By Ada"
// GET /Articles/Filter               → "All articles"
public IActionResult Filter(string? author)
    => Content(author is null
        ? "All articles"
        : $"By {author}");

Both URLs reach the same action. The action decides what a missing value means — that decision is ours, and it is worth making deliberately.

Then some data, and the first action

// A temporary in-memory list. Session 07 makes it a database.
private static readonly List<Article> _articles = new()
{
    new Article { Id = 1, Title = "How the web works", Author = "Ada" },
    new Article { Id = 2, Title = "Getting started", Author = "Grace" },
    new Article { Id = 3, Title = "Controllers 101", Author = "Ada" },

// GET /Articles
public IActionResult Index()
    => Content(string.Join("\n",
        _articles.Select(a => $"{a.Id}: {a.Title}")));
static so the list survives between requests — remember that the controller itself does not. Select is the LINQ from Session 02, doing real work for the first time.

Demo

One article, or an honest 404

// GET /Articles/Details/2
public IActionResult Details(int id)
{
    var article = _articles.FirstOrDefault(a => a.Id == id);
    if (article is null)
        return NotFound();

    return Content($"{article.Title} — {article.Author}");
}
Three lines of that method exist only to answer one question: what if it is not there?
Every action that takes an id needs those three lines. Writing them becomes automatic.
Microsoft Web Technologies

Demo

Filtering from the query string, and a static page

// GET /Articles/ByAuthor?author=Ada
public IActionResult ByAuthor(string? author)
{
    var matches = string.IsNullOrWhiteSpace(author)
        ? _articles
        : _articles.Where(a => a.Author == author).ToList();

    return Content($"{matches.Count} article(s)");
}

// GET /Articles/About
public IActionResult About()
    => Content("A tiny blog built during this course.");

Demo · the moment that matters

A missing article is not a crash

// /Articles/Details/999 — version one
var article = _articles.First(a => a.Id == id);
// nothing matches → exception → 500 Internal Server Error

// /Articles/Details/999 — version two
var article = _articles.FirstOrDefault(a => a.Id == id);
if (article is null) return NotFound();
// nothing matches → null → 404 Not Found
500 means our code broke. It is a bug report shown to a stranger.
404 means that article does not exist — a correct, deliberate answer. This is Session 01's "whose bug is it?" made concrete.

Wrap-up

Common misconceptions

MisconceptionCorrection
"MVC is a Microsoft technology."It is a 1970s user-interface pattern, used across every major web ecosystem.
"The model is the database."The model is the data and its rules. It may be stored in a database — a separate concern.
"The controller draws the page."It chooses a view and hands it data. Rendering is the view's job.
"The class name in the URL includes Controller."ArticlesController is reached at /Articles.
"One controller per page."One controller per area of responsibility, with many actions.
"The controller object lives as long as the app."A fresh instance per request, discarded afterwards.
"A missing record should throw."A missing record is a 404. An exception is a 500 — a different meaning entirely.
"Parameters are matched by position."They are matched by name.

Walkthrough · 40 min · together

We build a controller from an empty file

  1. We create Models/Article.cs with Id, Title, Author, Summary and PublishedOn.
  2. We create Controllers/ArticlesController.cs with a static List<Article> of five articles by two authors.
  3. We add Index() — a numbered list of titles — and Details(int id) with a real 404 for an unknown id.
  1. We add ByAuthor(string? author) and Recent(int days = 7), both with LINQ, both correct when the parameter is omitted.
  2. We add About() and Contact() returning static text.
  3. We visit all six actions with DevTools open and read every status code, then break Details back to First to watch the 500 — and fix it again.
By the end we will have six actions responding at the expected URLs, a Details that answers 404 for an unknown id — verified in DevTools, not merely "an error page" — and two actions that behave correctly when their parameter is missing.
