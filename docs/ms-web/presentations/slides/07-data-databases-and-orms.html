Storage that outlives the process: the relational model, a working

Lecture 4 · Models, ORM, EF Core setup~180 min

Where we are

Everything so far has been about the shape of an answer

Sessions 03–04

The request finds our code

Routing picks a controller and an action. The action returns a view. The Model is where the data lives — and so far, that model is a hard-coded list of articles.

The answer is rendered

This session

Block 1 · 10 min

Memory forgets

A demonstration first, an explanation second.

Microsoft Web Technologies

Memory forgets · demo

Where did it go?

  1. We run the app and open the article list. Three articles, as always.
  2. We add a fourth article while the app is running.
  3. We reload the page. It is still there. So far, so good.
  4. We stop the app and start it again.
  5. Three articles.

Nothing was deleted

No file was removed, no error was raised, no code is wrong. The fourth article was never anywhere that could survive step 4.

A list of articles held in memory belongs to the running program. When the program ends, the memory it was using is handed back — a restart, a deployment, a crash, a power cut. All the same thing.
Microsoft Web Technologies

Memory forgets

Losing the data is only the first problem

Three more, which a bigger memory would not fix:

  • Two copies of the app on two machines would each hold a different list. Which one is right?
  • Nothing coordinates two people editing the same article at the same instant.
  • "How many articles per author?" can only be answered by walking the whole list, every time.

So we need storage that is:

Durable

It outlives the program that wrote it.

Shared

One copy, many readers and writers.

Queryable

Questions answered without scanning everything.

Safe

Correct when several people write at once.

A plain file gives us the first one only. A database management system — a separate program whose whole job is storing and answering — gives us all four.

Block 2 · 30 min

The relational model

Tables, rows, columns and the keys that tie them together.

Microsoft Web Technologies

The relational model

The box we drew dashed in Session 01

A separate program

Not part of our app. It may not even run on the same machine. Our app is one of its clients.

Two roles again

Towards the browser our app is the server. Towards the database it is the client — it asks, and waits.

Its own language

The database does not understand our objects. It answers questions written in SQL, and returns rows.

Microsoft Web Technologies

The relational model

Analogy: the spreadsheet, taken seriously

Articles
+----+--------------------+---------+--------------+
| Id | Title              | Author  | PublishedOn  |
+----+--------------------+---------+--------------+
|  1 | How the web works  | Ada     | 2026-01-10   |
|  2 | Getting started    | Grace   | 2026-02-02   |
|  3 | Controllers 101    | Ada     | 2026-03-01   |
+----+--------------------+---------+--------------+
  ^^ primary key

What is the same as a spreadsheet

Named columns, rows of data, one sheet per kind of thing.

What a database adds

Columns have declared types. Rules are enforced, not merely intended. And questions are answered efficiently over millions of rows.

Microsoft Web Technologies

The relational model

Seven words, one line each

TermMeaning
TableOne kind of thing — articles, users, categories.
Row / recordOne of those things.
Column / fieldOne named property of it, with a declared type.
Primary keyThe column that uniquely identifies a row — never null, never reused.
Foreign keyA column holding another table's primary key. This is how tables relate.
SchemaThe whole structure: tables, columns, types, keys, constraints.
ConstraintA rule the database itself enforces — NOT NULL, UNIQUE, and others.
Types are not decoration. A published date stored as a real date can be sorted, compared and ranged over. Stored as text, it cannot — "10 March" sorts before "2 March". This is the single most common beginner mistake in a first project.
Microsoft Web Technologies

The relational model

Why not one giant table?

Suppose each article also carried its author's full name, biography and photo. Two hundred articles by Ada means two hundred copies of Ada. Change the photo and you change it in two hundred places; mistype the name once and you have invented a second Ada.

Articles                                  Authors
+----+-----------+----------+          +----+--------+-----+
| Id | Title     | AuthorId |--- FK -->| Id | Name   | Bio |
+----+-----------+----------+          +----+--------+-----+

Normalisation

Stated at the level we need it: store each fact exactly once, and point at it from wherever else it is needed.

How many on each side

One author has many articles; each article has one author. That is a one-to-many relationship — the only shape we need, and we will build one in Session 08.

Microsoft Web Technologies

The relational model

Which database? They differ in scale, not in ideas

Our default

A single-file database

The whole database is one ordinary file next to the project. No server to install, no service to start, no password. It is a real relational database with real SQL — just packaged as a file.

We use it so that every operating system in this room behaves identically.

The other family

Server databases

A permanently running program that listens on a port and accepts connections from many applications at once, with users, permissions and backups of its own.

Bigger deployments need this. Everything in the next three hours applies unchanged.

Tables, rows, keys, constraints and SQL are the same in all of them. Later in this session we will see exactly how much code has to change to swap one for the other. The answer is: two lines.

Block 3 · 20 min

A working minimum of SQL

Six statements will carry us through the whole course.

Microsoft Web Technologies

A working minimum of SQL

Asking questions

-- every article, two columns only
SELECT Title, Author FROM Articles;

-- only the rows that match
SELECT * FROM Articles WHERE Author = 'Ada';

-- filtered and sorted
SELECT * FROM Articles
WHERE  PublishedOn >= '2026-02-01'
ORDER BY PublishedOn DESC;

-- counted per author
SELECT Author, COUNT(*) FROM Articles
GROUP BY Author;

SQL is declarative

We describe the result we want, not the steps to produce it. Which rows to read in which order is the database's problem, and it is very good at it.

Four questions, over and over

Which rows? Which columns? In what order? How many? Nearly every read in this course is one of those four, or a combination.

Microsoft Web Technologies

A working minimum of SQL

Changing things

-- add a row
INSERT INTO Articles (Title, Author, PublishedOn)
VALUES ('New post', 'Ada', '2026-03-04');

-- change a row
UPDATE Articles
SET    Title = 'Edited title'
WHERE  Id = 3;

-- remove a row
DELETE FROM Articles
WHERE Id = 3;

The key does the aiming

Every one of these picks its target by primary key. That is what a primary key is for — one row, unambiguously.

We do not supply the Id

The INSERT names three columns, not four. The database generates the key. Remember this when we return to it in code.

Microsoft Web Technologies

Say it once, mean it forever

A DELETE or an UPDATE without a WHERE
applies to every single row.

There is no undo. There is no confirmation dialog. DELETE FROM Articles; empties the table and reports success. We will repeat this warning in Session 09, when we start writing deletes for real.

Microsoft Web Technologies

A working minimum of SQL · demo

We open the file and ask it something

  1. We open a sample database in a viewer — a database extension in the editor, or the command-line tool that ships with it.
  2. We look at the table list, then at one table's columns and their declared types.
  3. We run a SELECT with no WHERE and see every row.
  4. We add a WHERE, then an ORDER BY, and watch the result narrow and reorder.

Why we spend ten minutes on this

Everything after this point in the course is a program writing these same statements on our behalf. Having seen the rows with our own eyes, the rest of the session stops being abstract.

A database is not a mystery inside the framework. It is a file, or a service, holding tables you can look at.

Block 5 · 20 min

The object–relational mismatch

Our program thinks in objects. The database thinks in tables. Something has to translate.

Microsoft Web Technologies

The object–relational mismatch

The same article, described twice

Naming

One article, but a table of many: Article against Articles. Something must decide the plural.

Types

The two systems have different type names and different limits. Every value is converted in both directions.

Nullability

A column may hold nothing at all. A property in the program may not be prepared for that. Someone has to reconcile it.

Microsoft Web Technologies

The object–relational mismatch

Bridging it by hand, once

open a connection to the database

write  "SELECT Id, Title, Author, PublishedOn
        FROM Articles WHERE Id = ?"
bind  the parameter
run   it

for each row that comes back:
    build an Article
      Id          ← row["Id"]         as number
      Title       ← row["Title"]      as text
      Author      ← row["Author"]     as text
      PublishedOn ← row["PublishedOn"] as date

close the connection

Now do it again

For every query. In both directions. In every application ever written.

And notice the strings

Every column name is quoted text. Misspell one and nothing complains until the program runs and fails in front of a user.

Microsoft Web Technologies

The object–relational mismatch

What an ORM is, and where it sits

The definition

An object–relational mapper is a library that is told how classes correspond to tables, and from then on generates the SQL and builds the objects for us.

We never write that middle box

We ask a question in the language of our own objects. The SQL is produced from it.

But it is still SQL

The database understands nothing else. That is why we learned to read it first.

Microsoft Web Technologies

The object–relational mismatch

Be honest about the trade

You gainYou give up
No hand-written mapping code, ever again.Some control over the exact SQL that runs.
Property names checked before the program runs, not after.A whole extra layer that has to be learned.
One codebase across several database engines.Performance surprises when it is used carelessly.
Changes to the structure tracked in source control — Session 08. 
A mapper does not replace SQL. When a page is slow, the only way to find out why is to read the SQL the mapper produced. We do exactly that in Session 08 — which is why this session began with the language and not with the library.

Entity Framework Core

The entity: a plain class, and nothing more

// Models/Article.cs
namespace SimpleBlog.Models;

public class Article
{
    public int      Id          { get; set; }
    public string   Title       { get; set; } = "";
    public string   Author      { get; set; } = "";
    public string   Summary     { get; set; } = "";
    public string   Body        { get; set; } = "";
    public DateTime PublishedOn { get; set; }
}
  • A property named Id becomes the primary key. No attribute needed.
  • An integer key is generated by the database on insert — we leave it at 0.
  • Property names become column names; the types are mapped for us.
  • A string column is nullable unless we say otherwise — Session 08 fixes that with data annotations.
The class from Session 03 is unchanged in spirit. Note also what it is not: ArticleListViewModel from Session 06 is what a page needs. Article is what we store. They change for different reasons, which is exactly why they are two classes.
Microsoft Web Technologies

Entity Framework Core

The DbContext: the database, as an object

// Data/ApplicationDbContext.cs
using Microsoft.EntityFrameworkCore;
using SimpleBlog.Models;

namespace SimpleBlog.Data;

public class ApplicationDbContext : DbContext
{
    public ApplicationDbContext(
        DbContextOptions<ApplicationDbContext> options)
        : base(options) { }

    public DbSet<Article> Articles => Set<Article>();
}
  • The class stands for the database.
  • Each DbSet<T> stands for one table. The property name Articles becomes the table name — there is the plural from our diagram.
  • It takes options rather than deciding for itself which database it is. That single choice is what makes the next block necessary.
  • A DbSet<T> is queried exactly like the List<T> of Session 02.

The connection string

// appsettings.json
{
  "ConnectionStrings": {
    "DefaultConnection": "Data Source=simpleblog.db"
  },
  "Logging": { "LogLevel": { "Default": "Information" } },
  "AllowedHosts": "*"
}

Which database, where, and how do I get in

That is all a connection string is. Here it names a file that will sit beside the project.

Configuration, with a job at last

On the Session 02 folder tour appsettings.json was "the configuration file". This is the first thing we have actually put in it.

Security, now rather than later. Connection strings for real databases contain passwords, and appsettings.json is committed to source control. Real projects keep secrets in user-secrets (dotnet user-secrets init), environment variables or a key vault — never in a committed file. We return to this in Session 10.

Dependency injection

A class states what it needs. Something else decides what it gets.

Microsoft Web Technologies

Dependency injection

Why not just write new ApplicationDbContext()?

It is the obvious thing to type. Ask it out loud, then follow it through.

The controller decides the database

Which engine, which file, which server — decided inside a class whose job is answering one URL.

And every controller decides again

Change the provider and you edit forty files, hoping you found all of them.

Nobody closes it

The connection is opened per controller, and released whenever someone remembers to.

It cannot be tested

To test one action you need a real database, because the action insists on building one.

Every one of those is the same fault: a class that decides for itself what it depends on.
Microsoft Web Technologies

Dependency injection

Inversion of control, for the third time in this course

  • Session 02 — we do not call the framework; the framework calls our code.
  • Session 05 — the view does not draw the page around itself; the layout wraps it.
  • Session 07 — the controller does not build its database context; it is handed one.

The restaurant, once more

The waiter does not go to the market and does not choose the supplier. Supplies arrive at the kitchen door; the waiter simply uses them — and can carry on working if the supplier changes overnight.

A class declares what it needs.
Something else decides what it gets.

Microsoft Web Technologies

Dependency injection · demo

Registering the context, once, in Program.cs

using Microsoft.EntityFrameworkCore;
using SimpleBlog.Data;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllersWithViews();

builder.Services.AddDbContext<ApplicationDbContext>(options =>
    options.UseSqlite(builder.Configuration
        .GetConnectionString("DefaultConnection")));

var app = builder.Build();
Read it as one sentence: "whenever anything needs an ApplicationDbContext, build one using SQLite and the DefaultConnection string." builder.Services is the application's registry of what it is able to supply — AddControllersWithViews has been filling it since Session 02.
Microsoft Web Technologies

Dependency injection · demo

Asking for it, in the controller

public class ArticlesController : Controller
{
    private readonly ApplicationDbContext _context;
    public ArticlesController(ApplicationDbContext context)
    {
        _context = context;   // asked for, not created
    }

    public IActionResult Index()
    {
        var articles = _context.Articles
            .OrderByDescending(a => a.PublishedOn).ToList();
        return View(articles);
    }
}

Constructor injection

The dependency is a constructor parameter. The framework reads it, finds a match in the registry, and supplies one when it creates the controller for a request — step 4 of the Session 03 lifecycle.

Nobody writes new ArticlesController(…)

We never did. The framework has always created our controllers; now it fills in their needs as well.

Microsoft Web Technologies

Dependency injection

How long does the thing we are handed live?

LifetimeOne instance per…For a database context
Transientevery single request for itWasteful — a new connection story each time it is asked for.
Scopedone HTTP requestCorrect. AddDbContext registers scoped by default — we did not have to choose.
Singletonthe whole applicationWrong, and dangerously so.
A DbContext tracks the changes we make so it knows what to save. Two simultaneous requests sharing one tracker would see each other's half-finished edits. One request, one context, discarded at the end — that is what scoped means.

Wrap-up

Common misconceptions — data and SQL

MisconceptionCorrection
"A list is fine, it keeps my data."Only while the process lives. Restart and it is gone.
"A database is just a spreadsheet."It also enforces rules, answers queries efficiently, and handles many users at once.
"Store dates as text, it's simpler."Then you cannot sort or compare them correctly. Use date types.
"An ORM means I never need SQL."When a query is slow, reading the generated SQL is the only way to find out why.
"SQLite is a toy; the real course is SQL Server."Only the provider and the connection string differ. Everything you learn transfers.

Wrap-up

Common misconceptions — the context and its lifetime

MisconceptionCorrection
"DbContext is the database."It is an object representing a session with the database.
"Set the Id before inserting."The database generates it. Leave it at 0.
"new ApplicationDbContext() in the controller is simpler."It hard-codes the provider, leaks connections and makes testing impossible.
"One context for the whole app is efficient."It tracks changes and is not safe across concurrent requests. Scoped, per request.
"Connection strings are fine in appsettings.json."Not with a password in them. That file is committed to source control.

Walkthrough · 25 min · together

We wire up the database

We do it once on screen, in SimpleBlog, in this order. Follow along on your own machine and stop me at any step that does not land.

  1. We install the two packages and the tool, then open .csproj to see what changed.
  2. We reshape Article: Id, Title, Author, Summary, Body, PublishedOn.
  3. We create Data/ApplicationDbContext.cs with one DbSet<Article>.
  4. We add ConnectionStrings:DefaultConnection to appsettings.json.
  1. We register it in Program.cs with AddDbContext and UseSqlite.

  3. We run it, read the error aloud, and name in one sentence exactly what is missing.
By the end we will have a project that compiles, contains no new ApplicationDbContext() and no static list, queries through the injected context — and fails at runtime for one precise reason we can all state.
