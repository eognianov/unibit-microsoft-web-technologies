How to find a bug

A method, not a talent. Nothing in this block belongs to any one language.

Microsoft Web Technologies

How to find a bug

Debugging is a method, not a talent

Beginners debug by changing things until the error stops. That is slow, and it teaches nothing.

  1. Reproduce it reliably. A fault we cannot trigger on demand cannot be fixed, only guessed at. We write down the exact steps.
  2. Read the error message. All of it — the file, the line, the innermost cause. This is the step everyone skips.
  3. Form one hypothesis. "The id is arriving as 0." Not "something is wrong with the database."
  4. Test that one hypothesis — with a pause point or a log line.
  1. Narrow the search. Confirm where the value is still right and where it is already wrong. Halve the interval each time.
  2. Fix the cause, not the symptom. Wrapping a crash in error handling so it stops crashing is not a fix.
  3. Verify. Reproduce the original steps and confirm the behaviour changed.

The rule that saves the most time

We are not looking for the bug.
We are looking for the first place the state is wrong.

Everything after that point is a consequence. The crash is usually a long way downstream of the mistake.

How to find a bug

Three tools, three different purposes

Now

The debugger

Inspecting state at a moment, in detail. Every variable, at once, without editing the code.

Later

Logging

What happened over time — especially on a machine we cannot pause and poke at.

Session 01

Browser DevTools

What actually crossed the wire: the method, the path, the status code, the headers.

Choosing the wrong one costs hours. "It returns the wrong page" is a DevTools question. "The value is wrong by the time it gets here" is a debugger question. "It failed once, at 3 a.m., for one user" is a logging question.
Microsoft Web Technologies

How to find a bug

What a debugger actually does

A breakpoint tells the running program to pause on a line, before executing it. While paused, the program is frozen and inspectable.

ActionMeaning
ContinueRun until the next breakpoint.
Step overRun this line; do not go inside the calls it makes.
Step intoGo inside the call on this line.
Step outFinish this piece of code and return to whoever called it.

Locals

Every variable in scope, right now, with its current value.

Watch

Expressions we chose to keep an eye on, re-evaluated at every pause.

Call stack

Who called whom to get here. Read it bottom-up to answer "how did we reach this line?"

Microsoft Web Technologies

Said plainly

A debugger is not for emergencies.

Stepping through code we just wrote — while it works — is the fastest way to learn what it really does. Most people first open a debugger in a panic, years too late.

Demo · live investigation

A planted bug, found with the debugger

Details returns 404 for an article that exists. The parameter is named articleId; the route says {id} — Session 04's contract, broken on purpose.

  1. We press F5 — in VS Code with the C# Dev Kit, or in Visual Studio. The app starts with the debugger attached.
  2. We set a breakpoint on the first line of Details and request /articles/2. Execution pauses.
  3. Locals: id is 0, not 2. There is the first wrong value.
  4. Call stack: we read who invoked the action.
  1. Watch: we add _context.Articles.Count() and evaluate it against the live database while paused.
  2. We step over FirstOrDefaultAsync and watch article become null.
  3. Diagnosis: model binding never matched a value to the parameter. We fix the name, and we verify by repeating step 2.

Past the plain breakpoint

id == 42

Conditional breakpoints

Right-click a breakpoint and give it a condition. Priceless inside a loop over 500 rows, where stopping every time is useless.

on throw

Break where it was thrown

Breaking on a thrown exception stops us where the exception happened, not where it finally surfaced. Those are rarely the same place.

dotnet watch

The debugger evaluates expressions against the live process. A watch on a database query runs a real query, against the real data, at the moment we are paused.

Error pages: two audiences

The same exception. Two completely different screens — and the same status code.

Microsoft Web Technologies

The idea

When something throws, who is looking?

Us, developingA user, on the live site
NeedsThe error, the trace of how we got there, the line of code, the query."Something went wrong. Please try again."
Must not see—File paths, source code, database connection details, table names, versions.
Where the detail goesStraight onto the screen.Into the log, where only we can read it.
A full error trace on a public site tells an attacker which framework we use, which versions, how our files are laid out, and often the structure of our database. It is free reconnaissance.
Microsoft Web Technologies

The rule

Detailed diagnostics in development.
A generic apology in production.

The real details still exist — they go to the log. The user gets an apology and a way forward; we get the evidence.

Microsoft Web Technologies

In practice · .NET 10

The template already wrote this — now it means something

// Program.cs
if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler("/Home/Error");
    app.UseHsts();
}

// no-exception status codes get a friendly page too
app.UseStatusCodePagesWithReExecute("/Home/Error/{0}");
  • In Development the detailed page is on by default — no line of code needed.
  • Anywhere else, the exception handler re-runs the request at /Home/Error and shows the generic page.
  • The last line covers a NotFound() — a 404 with no exception behind it, which the handler above would never see.
Properties/launchSettings.json is where the Development environment name comes from on our own machine. It is a local file, and it is not what runs on a server.
Microsoft Web Technologies

Demo · both screens

Same exception, same status code, different disclosure

Development 
$ dotnet run

The developer exception page: the message, the stack trace, the highlighted source line, the request headers, the route values. Everything we asked for on the previous slide.

Production 
$ ASPNETCORE_ENVIRONMENT=Production dotnet run
# PowerShell:
$env:ASPNETCORE_ENVIRONMENT="Production"; dotnet run

The generic /Home/Error page. No message, no trace, no file names — an apology and nothing else.

We check DevTools for both: both return HTTP 500. Session 01 closes here — the status code is the same, the disclosure is not. The status code is for machines; the page is for people.

Block 6 · 20 min · talk and demo

Logging

Levels, what to log, and what must never appear in a log as long as we live.

Microsoft Web Technologies

The idea

Six levels, and the question each one answers

Printing to the console does not survive deployment — on a server there is no console for anyone to watch. A logging framework adds levels, filtering, timestamps and somewhere durable to write.

LevelThe question it answersExample
TraceEvery detail, no matter how small.Rarely switched on at all.
DebugWhat is happening internally?"Query returned 12 rows."
InformationWhat normal, notable thing happened?"Article 42 created by Ada."
WarningOdd — but we handled it."Article 999 not found."
ErrorThis operation failed."Saving article failed."
CriticalThe application itself is in trouble."Database unreachable."
Microsoft Web Technologies

The idea

A level is a filter, and the filter is configurable

Microsoft Web Technologies

The idea

What to log, and what must never be logged

Log the events, not the noise

A log nobody reads is worse than no log — it hides the one line that mattered under ten thousand that did not.

Include the identifiers

Whatever we would need to investigate: which article, which user, which request. "An error occurred" helps nobody.

Log at the boundaries

Things entering the application, things leaving it, and every error we caught and handled quietly.

Never

Secrets and personal data

Passwords, tokens, database credentials, card numbers, anything private about a person.

Logs are copied to other machines, shipped to other services, and read by people who were never meant to see the underlying data. Once it is in a log, it is everywhere.

This is a legal question as much as a technical one.

Microsoft Web Technologies

In practice · .NET 10

Logging is already registered — we just ask for it

public class ArticlesController : Controller
{
    private readonly ApplicationDbContext _context;
    private readonly ILogger<ArticlesController> _logger;

    public ArticlesController(ApplicationDbContext context,
                              ILogger<ArticlesController> logger)
    {
        _context = context;
        _logger = logger;
    }
}
  • ILogger<T> arrives by dependency injection — exactly the mechanism that hands us the database context since Session 07.
  • Nothing to configure, nothing to install. The type parameter is just the class doing the logging, so every line is stamped with where it came from.
Microsoft Web Technologies

In practice · .NET 10

Structured logging: the braces are not string formatting

public async Task<IActionResult> Details(int id)
{
    var article = await _context.Articles.FindAsync(id);

    if (article is null)
    {
        _logger.LogWarning("Article {ArticleId} missing.", id);
        return NotFound();
    }

    _logger.LogInformation("Serving article {ArticleId}.", id);
    return View(article);
}

Named placeholder

{ArticleId} is a name, not a position. The value is stored beside the message, so a log system can answer "show me every line where ArticleId = 42" across millions of rows.

String interpolation

Writing $"Article {id} saved" produces the same text on screen and throws the structure away. Same output, none of the searchability.

In practice · .NET 10

Where the threshold lives

// appsettings.json
"Logging": {
  "LogLevel": {
    "Default": "Information",
    "Microsoft.AspNetCore": "Warning",
    "Microsoft.EntityFrameworkCore
      .Database.Command": "Information"
  }
}
  • Each key sets the threshold for one part of the application. Default catches everything else.
  • That last entry is what has been printing generated SQL to our console since Session 08. We switch it to Warning and watch the console go quiet.
  • appsettings.Development.json overrides appsettings.json. That is how one codebase behaves differently in two places — no if statements anywhere.

Deployment

What has actually been running our site all course? A laptop. Let us fix that.

Microsoft Web Technologies

The idea

What has to be true for it to be a website?

RequirementOn our machineIn production
A machine that is always onA laptop, until the lid closes.A server, or a cloud service.
A public addresslocalhost:5001 — visible to nobody else.A domain name, resolved by DNS (Session 01).
Encrypted trafficA development certificate the machine trusts.A real certificate, issued for that domain.
A reachable databaseA file next to the project.A hosted database with its own credentials.
Restart after a crashWe press play again.The host does it, unattended, at 3 a.m.
Configuration and secretsA file in the project folder.Settings held by the host, outside the code.
Microsoft Web Technologies

The idea

Every deployment, in any technology, is two steps

Step 1

Build

Turn source code into an optimised set of files that can be run. Not our source — the output.

Step 2

Host

Put those files on a machine configured to run them and answer requests, forever, without us.

Three ways to arrange the second step:

Our own server

Full control, and full responsibility: operating system, updates, certificates, backups, the lot.

A platform service

We supply the application; they supply the machine, the restarts and the certificate.

Containers

We ship the application and its environment, so "works on my machine" becomes "ships as my machine".

Microsoft Web Technologies

The idea

The same code must behave differently in different places

Not this

A condition in the code

Deciding inside the program which database to use, or whether to show the error detail, means the decision ships with the code and can only change by changing the code.

This

A named environment, set outside

The machine tells the application which environment it is running in. The application loads the settings for that name: verbose errors here, silence there; this database here, that one there.

One codebase, several environments, no branches and no commented-out lines. We saw the mechanism already in the logging settings — the same idea decides every other difference too.

In practice · .NET 10

The artifact: what actually gets deployed

$ dotnet publish -c Release -o ./publish

$ ls ./publish
SimpleBlog.dll   SimpleBlog.deps.json
appsettings.json  web.config
wwwroot/          # and the runtime files
No .cs files anywhere. This folder is the artifact. This is what gets deployed — not our project folder.
  • -c Release: optimised, with debug information stripped. Debug is for our machine only, and it is slower.
  • wwwroot travels as-is — our stylesheets and Bootstrap files from Session 06 are static content, not compiled.
  • appsettings.json travels too. Which is exactly why the production password must not be in it.

In practice · demo from the front

Publishing to Azure App Service

From the command line 
$ az webapp up --name simpleblog-ada \
    --runtime "DOTNET:10" --sku F1

One command: it creates the hosting plan, creates the web app, builds, uploads and gives us a public URL.

From the editor

VS Code: the Azure extension → Deploy to Web App.

Visual Studio: right-click the project → Publish → App Service → create a publish profile → Publish.

We open the Properties/PublishProfiles/*.pubxml file it writes: a saved recipe of where and how to publish. Not magic, and worth reading once.

Accounts. We run this once from the front, on one account, and everybody watches the same deployment. Repeating it individually needs an Azure account of your own — the free F1 tier is enough, and a student account covers it.

In practice · where the real lesson is

Publishing was the easy part. Now configure it.

Production

The environment name

ASPNETCORE_ENVIRONMENT is Production by default on App Service. That single value is what switches off the developer exception page.

Critical

The connection string

Set it as an application setting in the portal — never in the committed appsettings.json. Session 07's warning, now unavoidable: the host's setting wins over the file.

On

HTTPS

The platform supplies a certificate for its domain. We confirm the setting that refuses plain HTTP altogether.

Following along here needs an Azure account of your own. Watching is enough — the three settings are the point, and every hosting platform on earth has the same three.

In practice · .NET 10

Migrations against a database that has real data in it

$ dotnet ef migrations script --idempotent \
    -o migrate.sql

--idempotent produces SQL that checks what has already been applied, so running it twice is harmless. We open the file and read the guard around each migration.

Running dotnet ef database update against production from a laptop is not a habit to acquire. Generate the script, review it, let a pipeline or a DBA apply it.
  1. Back up the production database. Every time.
  2. Review the script — especially anything that drops or renames a column (Session 08's warning about guessed renames).
  3. Apply the script.
  4. Deploy the new code.
  5. Verify, and know how to roll back before we need to.
Microsoft Web Technologies

In practice · one honest caveat

The tempting shortcut, and why it is a trap

// convenient. also a trap.
context.Database.Migrate();

Calling this at start-up means the application updates its own schema whenever it launches. For a course project that is genuinely fine, and we may well use it.

Why it is not the professional default

With several copies of the application starting at once, they race each other to alter the same schema.

It also grants the running web application permission to change the database structure — a permission a web front end should not hold.

Fine for a student project. Say out loud that you know why it is not the default.

The final project

Build a data-driven ASP.NET Core MVC application
of your own choosing — not the blog.

Pick a domain you actually care about: a recipe collection, a football league, a film library, a bug tracker. Two entities, one relationship, and everything this course has taught you.

Microsoft Web Technologies

The final project

Minimum requirements

  • At least two related entities (one-to-many), created code-first with migrations.
  • Full CRUD for the main entity, with all four operations working.
  • Server-side validation with meaningful messages, plus client-side hints.
  • Anti-forgery tokens on every POST; nothing that changes state on a GET.
  • At least five views using a shared layout and at least one partial.
  • Responsive with Bootstrap; usable at 375px and at 1440px.
  • Designed URLs — readable and consistent, on Session 04's principles.
  • Seed data, so the application is not empty on first run.
  • View models, not entities, wherever a page needs more or less than one entity.
  • A README.md: what it does, how to run it, what you would do next.

The final project

How to approach it

  1. Choose a domain and write down the two entities and the relationship between them, in one sentence, before writing any code.
  2. Build it in the order the course did: routes and controllers, then views and layout, then the model and migrations, then CRUD and validation, then error handling and polish.
  1. Commit as you go, with meaningful messages. The history is part of the story you tell at the defence.
  2. Write the README.md first, not last. It forces you to decide what the application actually is while it is still cheap to change your mind.
Scope it so that everything on the requirements list works, rather than so that half of an ambitious idea works. A small, complete, defensible application scores higher than a large broken one — every time.

Common misconceptions · debugging and errors

MisconceptionCorrection
"Debugging means adding print statements."The debugger shows every variable at once, without editing a single line of code.
"The debugger is for emergencies."Stepping through code that works is the fastest way to understand it.

Common misconceptions · deployment

MisconceptionCorrection
"Deploying means copying my project folder."You deploy the published output, not the source.
