CRUD, forms, and the two-request dance

Four operations, one HTML element, and why creating one record takes three requests.

Microsoft Web Technologies

CRUD

Four operations, in every language ever written

LetterOperationHTTPTypical URL
CCreateGET the form, then POST the data/articles/create
RReadGET/articles, /articles/42
UUpdateGET the filled form, then POST the changes/articles/42/edit
DDeleteGET the confirmation, then POST the deletion/articles/42/delete
Read is already done — that was Sessions 03 to 08. This session is the other three letters. Notice that every one of them needs two requests, and that even delete is a POST.
Microsoft Web Technologies

Forms

A form is the browser's built-in way to send data

<form action="/articles/create" method="post">

  <label for="title">Title</label>
  <input type="text" id="title"
         name="title" />

  <button type="submit">Save</button>

</form>
  • action — where the data goes.
  • method — how: get puts the values in the query string, post puts them in the request body. A form can only do these two — which is why delete is a POST.
  • name — the key each value is sent under.
Microsoft Web Technologies

The single most common beginner bug

No name, no value sent.

A field with no name attribute still looks perfect on screen, still accepts typing, still submits with the form — and contributes nothing to the request body. The server sees an empty field and you go looking for the bug in the wrong place.

We remove one name on screen, submit, and read the request body together. Once seen, never forgotten.

Microsoft Web Technologies

The crucial insight

Creating one record takes three requests

1.  GET  /articles/create   → an empty form        200 + HTML
    … the user types …
2.  POST /articles/create   → data received, saved 302 redirect
3.  GET  /articles         → the browser follows  200 + HTML

Two of them are ours to write

One request shows the form; a second one receives it. The third the browser makes on its own.

One URL, two handlers

The same address answers both — told apart by the method, exactly as previewed in Session 04.

Nothing is remembered in between

Every request is independent (Session 01). Everything the second request needs, the form must carry.

Block 3 · 20 min

Never trust the client

The most important idea of the session — and the pattern that keeps a refresh from doing damage.

Microsoft Web Technologies

Never trust the client · say it slowly

Every rule in the page is advice to a cooperating browser

1

Edit the page

Open the developer tools, delete the attribute that says the field is required, submit the form. It took four seconds.

2

Skip the page

Send the request from a command-line tool and never load the form at all. The server cannot tell the difference — it only receives a request.

3

Replay it, changed

Capture a request that worked, alter a value, send it again.

Checking in the page is a convenience: it gives instant feedback and saves a round trip. Checking on the server is the security boundary. Have both — but if you may only have one, keep the server.
Microsoft Web Technologies

Never trust the client

The two walls, and why only one of them counts

Microsoft Web Technologies

POST/Redirect/GET

What goes wrong if we just answer a POST with a page

The user saves an article. We send back the list page as the response to that POST. The address bar now holds a URL that was reached by posting data.

Then they press Refresh

Refresh means "do that request again" — and that request was the POST. A second article appears. Nobody asked for it.

Then they press Back

Same problem, plus a URL nobody can bookmark, share or reload.

Everyone in this room has seen a browser ask "Confirm form resubmission". That dialogue is not a browser feature — it is a browser apologising for this bug, in the wild.
Microsoft Web Technologies

POST/Redirect/GET

Answer a POST with a redirect, never with a page

Microsoft Web Technologies

POST/Redirect/GET

The pattern has a name because it is universal

After a successful POST, never return HTML. Return a redirect, so the browser goes and asks for the result page with a fresh GET.

302

The callback from Session 01

The status-code table in Session 01 said: 302 Found — temporary redirect, for example after submitting a form (Session 09). This is that form.

Refresh becomes harmless

The last request the browser made was a GET. Repeating it changes nothing — it is safe, in Session 01's exact sense of the word.

The URL is honest again

What sits in the address bar is the page the user is looking at. It can be bookmarked, shared and reloaded, and Back behaves.

The redirect carries a Location header naming where to go. The browser follows it by itself — the user never sees the intermediate response, only two rows in the network log.

Razor forms and tag helpers

The same three ideas, now in ASP.NET Core MVC on .NET 10 — the action pair, model binding, and attributes that write the HTML for us.

Microsoft Web Technologies

The action pair

Two methods, one URL, told apart by the verb

[HttpGet]                          // GET /articles/create
public IActionResult Create() => View();

[HttpPost]                         // POST /articles/create
[ValidateAntiForgeryToken]
public async Task<IActionResult> Create(Article article)
{
    if (!ModelState.IsValid)
        return View(article);      // keep what they typed

    _context.Articles.Add(article);
    await _context.SaveChangesAsync();

    return RedirectToAction(nameof(Index));
}
Microsoft Web Technologies

The action pair

Five things to notice, in order

  1. Two methods with the same name, separated by [HttpGet] and [HttpPost]. This is what the method attributes in Session 04 were for.
  2. Model binding (Session 03) now fills a whole object, matching form field names to property names. We never read the request body by hand.
  3. return View(article) on failure — not return View(). Otherwise everything the user typed is wiped and they will never forgive us.
  4. nameof(Index) rather than "Index": renaming the action becomes a compile error instead of a broken link.
  5. SaveChangesAsync is the line that actually issues the INSERT — we watch it appear in the SQL log from Session 08.
Microsoft Web Technologies

Model binding · the sharp edge

Over-posting: binding fills fields we never put on the form

Article has an Id. Our form does not show it — but if someone adds Id=999 to the request body, model binding sets it anyway. On a richer model the same trick sets IsAdmin or IsPublished.

// Defence 1 — an allow-list of bindable properties
public async Task<IActionResult> Create(
    [Bind("Title,Author,Summary,Body,PublishedOn")] Article article)

// Defence 2 — bind to a view model holding only those fields
public async Task<IActionResult> Create(ArticleFormViewModel form)
Both work. The second is better, and is the reason Session 06 exists: the form binds to a type that cannot express the fields we are protecting, then we copy across to the entity by hand.
Microsoft Web Technologies

Tag helpers

Server-side attributes that generate the right HTML

@model SimpleBlog.Models.Article

<form asp-action="Create" method="post">
  <div asp-validation-summary="ModelOnly"></div>
  <div class="mb-3">
    <label asp-for="Title" class="form-label"></label>
    <input asp-for="Title" class="form-control" />
    <span asp-validation-for="Title"></span>
  </div>
  <!-- Author, Body, PublishedOn: three lines each -->
  <button type="submit">Save</button>
  <a asp-action="Index">Cancel</a>
</form>
  • Hand-written HTML forms are verbose, and drift out of step with the model the moment either changes.
  • A tag helper is an ordinary HTML element with an extra attribute the server understands and removes.
  • The browser never sees asp-for. It sees plain HTML.
Microsoft Web Technologies

Tag helpers

We open View source and read what one attribute produced

<input class="form-control" type="text" id="Title" name="Title"
       value="How the web works" maxlength="200"
       data-val="true"
       data-val-required="Please enter a title."
       data-val-length-max="200" />

name, id, value

From the property name and the current model value. The name is what model binding will match on the way back.

type, maxlength

From the data annotations we wrote in Session 08 — [DataType], [MaxLength].

data-val-*

The same rules, restated so the browser can check them before submitting.

We wrote those rules once, on the model. They now shape the database column, the form field, the check in the browser and the check on the server. This is the moment data annotations pay for themselves.
Microsoft Web Technologies

Tag helpers

The five we use in this course

Tag helperWhat it does
asp-forName, id, value, input type, and the client-validation attributes — all from one property.
asp-action · asp-controller · asp-route-*Generates the URL from the routing table, rather than us typing a string (Session 04).
asp-validation-forThe error message for one field.
asp-validation-summaryA block of messages: All, ModelOnly or None.
asp-itemsThe <option> elements of a <select>.
Every one of them disappears before the response leaves the server. Nothing on this list is a browser feature.
Microsoft Web Technologies

Tag helpers

Turning on the messages that appear as you type

Those data-val-* attributes do nothing on their own. A small script library reads them and shows the messages before the form is submitted — the project template already ships it as a partial view.

@section Scripts {
    <partial name="_ValidationScriptsPartial" />
}

With it

Errors appear the moment the field loses focus. No request is sent at all.

Without it

The same errors appear after a round trip to the server. Same messages, later moment.

We show the form both ways on screen. The point is that the server check runs in both cases — removing the script removes the convenience, not the protection.

Validation on the server

Annotations for the rules a type can express, ModelState for everything else.

Microsoft Web Technologies

Validation

The rules live on the model, next to the data

[Required(ErrorMessage = "Please enter a title.")]
[StringLength(200, MinimumLength = 5,
    ErrorMessage = "The title must be 5 to 200 characters.")]
public string Title { get; set; } = "";

[Required, EmailAddress]
public string ContactEmail { get; set; } = "";

[Range(0, 10_000)]
public int ReadingMinutes { get; set; }

[RegularExpression(@"^[a-z0-9-]+$")]
public string Slug { get; set; } = "";
Microsoft Web Technologies

Validation

ModelState is the record of what arrived and what was wrong with it

  • It is filled in automatically during model binding — before a single line of our action runs.
  • It holds, per field: the raw value that arrived, and any error messages attached to it.
  • IsValid is simply "is that error list empty".
  • Because it holds the raw values too, return View(article) can redisplay exactly what the user typed, error messages and all.
if (!ModelState.IsValid)
    return View(article);
Two lines. They are the entire security boundary for input in this application — the wall the crafted request in our diagram ran into.
Microsoft Web Technologies

Validation

The rules an annotation cannot express

Anything needing the database, another field or the current date, we check ourselves — reporting it into the same ModelState.

if (await _context.Articles.AnyAsync(a => a.Title == article.Title))
    ModelState.AddModelError(nameof(article.Title),
        "An article with this title already exists.");

if (article.PublishedOn > DateTime.Today.AddYears(1))
    ModelState.AddModelError(nameof(article.PublishedOn),
        "That date is too far in the future.");

if (!ModelState.IsValid) return View(article);
An error added with an empty key — AddModelError("", "…") — belongs to no field, so it appears in the ModelOnly summary at the top of the form.

CSRF, and the rest of CRUD

An attack that uses nothing but a form and your own cookies — then Edit and Delete.

Microsoft Web Technologies

CSRF · cross-site request forgery

The attack, told as a story

<!-- a page on someone else's site,
     open in another tab -->
<form action="https://yourblog.example/articles/5/delete"
      method="post" id="f"></form>

<script>
  document.getElementById('f').submit();
</script>
  1. We are logged in to our own blog in one tab.
  2. We open an unrelated page in another tab. It submits that form by itself.
  3. The browser sends it — and attaches our cookies, because it always sends that site's cookies to that site.
  4. Our server sees a valid, authenticated request to delete article 5. Nothing about it is malformed.
Microsoft Web Technologies

CSRF · the defence

A secret the attacker's page cannot know

Microsoft Web Technologies

CSRF · the defence

In ASP.NET Core this is nearly automatic

The form already emits it

Any <form> using a tag helper writes a hidden field for us. We find it in View source:

<input name="__RequestVerificationToken" type="hidden" value="CfDJ8…" />

The action demands it

[ValidateAntiForgeryToken] on the POST action makes the server require the field and check it before our code runs.

[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Delete(int id) { … }
We delete the hidden field in the developer tools and submit: 400 Bad Request — Session 01's status code, now with a reason attached to it.
Microsoft Web Technologies

Two rules, no exceptions in this course

1 · Every state-changing POST carries
[ValidateAntiForgeryToken].

2 · A GET never changes state.

A token cannot protect a GET: an <img src="…"> on any page in the world triggers one, and there is no form to put a token in. That is Session 01's rule about safe methods, arriving with teeth.

Microsoft Web Technologies

Security · where we already stand

Three attacks this session touches

Already safe

SQL injection

Input concatenated into a query changes what the query means. EF Core parameterises everything — we saw @__p_0 in the Session 08 log. Never build SQL with string concatenation.

Already safe

XSS

Input rendered back as HTML runs as code. Razor encodes output by default (Session 05). @Html.Raw switches that protection off — which is the only reason it is worth knowing it exists.

We must act

CSRF

Nothing protects us by default except the token, and the token only works if the attribute is on the action.

Being safe from one attack is not being safe. Over-posting is a fourth, and it is closed by neither the ORM nor the encoder — only by the allow-list or the view model.
Microsoft Web Technologies

Update

Edit is the same shape, with the form pre-filled

// the GET is Find, 404 if missing, View(article) —
// exactly the shape we used for Details in Session 03

[HttpPost, ValidateAntiForgeryToken]
public async Task<IActionResult> Edit(int id, Article a)
{
    if (id != a.Id) return BadRequest();
    if (!ModelState.IsValid) return View(a);
    _context.Update(a); await _context.SaveChangesAsync();
    return RedirectToAction(nameof(Index));
}
  • The GET loads the row and passes it to the view, so every field starts filled. An unknown id returns NotFound() — Session 03's rule, unchanged.
  • The URL and the body must agree about which row this is, or we refuse.
  • The form needs a hidden <input asp-for="Id" />, or the id never comes back.
Wrapping SaveChangesAsync in try/catch (DbUpdateConcurrencyException) is Session 02's exception handling with a real purpose: someone else may have deleted the row while this user was typing.
Microsoft Web Technologies

Delete · step 1 of 2

First a confirmation page — and it is a GET

[HttpGet]
public async Task<IActionResult> Delete(int id)
{
    var article = await _context.Articles
        .AsNoTracking()
        .FirstOrDefaultAsync(a => a.Id == id);

    if (article is null) return NotFound();

    // a page showing what is about to be lost
    return View(article);
}
  • This request only reads. It is safe, it is idempotent, and it may be repeated freely.
  • AsNoTracking() because we are displaying, not modifying — Session 07.
  • The page it returns holds a form with a single red button, and nothing else that can be clicked by accident.
Microsoft Web Technologies

Delete · step 2 of 2

Then the deletion — a POST, with a token

[HttpPost, ActionName("Delete")]
[ValidateAntiForgeryToken]
public async Task<IActionResult> DeleteConfirmed(int id)
{
    var a = await _context.Articles.FindAsync(id);

    if (a is not null)
    {
        _context.Articles.Remove(a);
        await _context.SaveChangesAsync();
    }

    return RedirectToAction(nameof(Index));
}
  • [ActionName("Delete")] lets a differently named method answer the Delete URL — needed because C# cannot have two methods with the same name and the same signature.
  • Deleting something already gone is not an error. We redirect either way.
Microsoft Web Technologies

Delete

Why the deletion can never be a GET

Session 01 put it as a warning: "if your delete is a GET, a crawler can wipe your database just by following links." Here is the concrete version of that sentence.

Crawlers follow links

A search engine visits every link it finds, unasked. A link that deletes is a link it will click.

Browsers repeat GETs

Prefetch, the back button, refresh, a restored tab. All of them re-issue a GET without telling anyone.

A token cannot help

There is no form, so there is nothing to carry a token. The only defence is that the URL is not destructive.

Real systems often soft delete instead: set IsDeleted = true and filter it out of every query, rather than removing the row. Worth considering for a final project — it makes "undo" possible.

Wrap-up

Common misconceptions · 1 of 2

MisconceptionCorrection
"Client-side validation is enough."It is a convenience. Anyone can bypass it. The server is the boundary.
"One action per page, so one action per form."A form needs a pair: a GET to show it, a POST to receive it.
"Return the page after a POST."Redirect. Otherwise a refresh re-submits it.
"return View() after a validation failure."return View(model) — otherwise the user's input is wiped.
"An input without name still submits."It sends nothing at all.
"Model binding only fills simple parameters."It fills whole objects by property name — including fields we did not intend (over-posting).

Common misconceptions · 2 of 2

MisconceptionCorrection
"[ValidateAntiForgeryToken] is optional for small sites."CSRF does not care how small the site is.
"The token protects GET requests too."It cannot. A GET must not change state.
"Delete needs one action."Two: a GET confirmation and a POST that deletes.
"Scaffolding writes production code."It writes a first draft bound to the entity, with no product decisions in it.
"EF Core makes me safe from SQL injection, so I am safe."From that one attack. XSS, CSRF and over-posting are separate problems with separate defences.

Walkthrough · 25 min · on screen

Full CRUD for Article, by hand

  1. We write Create: a GET showing an empty form with a tag helper for every field, and a POST that validates, saves and redirects to the list.
  2. We add the rules: Title required and 5–200 characters with our own message, Author and Body required, plus a custom error rejecting a duplicate title.
  3. We write Edit: GET pre-filled with the hidden Id field, 404 for an unknown id, POST updating and redirecting.
  4. We write Delete: a GET confirmation page, and a POST that removes the row behind a red button.
  1. We put [ValidateAntiForgeryToken] on every POST and find the hidden field in each form.
  2. We add _ValidationScriptsPartial and watch the messages appear before submission.
  3. We wire Create, Edit and Delete buttons onto the list page with asp-action and asp-route-id.
  4. We break it three ways on purpose: an empty title; required removed in the developer tools; the anti-forgery field deleted.
By the end we will have all four operations working end to end against the database: invalid input rejected by the server with the user's typing preserved, every POST carrying and checking a token, and nothing changing state on a GET.
